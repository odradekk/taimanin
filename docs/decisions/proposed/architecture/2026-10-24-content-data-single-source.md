# 战斗数值只写在内容数据里

Status: proposed

## Problem

同一个数值如果存在几处，调整时就要改几处，漏改时没有任何测试能发现。战斗第一版要写大量数值：8 名角色所有技能的倍率、消耗和架势削减（雪风以外的 7 人还缺 2 个忍术），雪风和凛子两棵天赋树，敌人的属性、技能和行动规则表，以及每个任务的首领。这些数值可能出现在三个地方：

- 设计文档。[combat.md](../../../design/combat.md) 已经带了一部分数值，比如雪风的完整技能表，并注明它们是初始值、实现后要调整。
- `src/content/` 下的内容数据，规则代码只从这里读数值。
- 界面上显示的说明文字。现在天赋节点的说明 `desc` 是手写的，比如「速度 +1.5%」，同一个数字在属性加成 `mods` 里还有一份。第一版要写 160 多条说明：8 名角色各 8 个技能和被动，3 棵天赋树里的 72 个属性节点和 27 个技能节点、核心节点。

## Proposal

- 角色技能、天赋、敌人和首领的具体数值只写在内容数据里，之后加入的道具和临时装备也一样。[architecture.md](../../../codebase/architecture.md) 第 3 节「数值」已经规定全局数值集中在 `content/balance.ts`、公式只在规则代码里写一次；这条决定把同样的做法用到每个角色和敌人的数值上。
- combat.md 保留规则和示例，开头写明具体数值以内容数据为准。调整数值时只改内容数据。
- 因为数值只在内容数据里，新的技能、天赋、敌人和首领也直接写成内容数据，不先在文档里列表。由 agent 按角色档案（`docs/lorebook/characters/`）和 combat.md 起草，维护者在 PR 里审。
- 说明文字的句子手写，数字用占位符从同一条技能或天赋的内容数据填入，例如「雷遁弹的麻痹基础概率提高到 {chance}%」。天赋和技能的数值会乘以资质系数（[character-progression.md](../../../design/character-progression.md) 第 7 节「资质与淬炼」），所以界面可以填入按角色当前资质换算后的数值。占位符的具体写法在实现时确定。
- 内容校验测试检查每个占位符都能在对应的内容数据里找到。

## Alternatives considered

**先把数值补进 combat.md，每名角色一张完整技能表、每种敌人一张属性和行动表，审定后再写成内容数据。** 在文档里能横向比较、审视平衡。没有选，因为数值会在文档和内容数据里各存一份。

**由维护者写技能、天赋、敌人和首领，agent 只实现机制。** 没有选，因为这些内容不需要维护者亲自写，由 agent 起草、维护者审就够了。

**说明文字和数字都手写。** 最简单，也是现在天赋节点的写法。没有选，因为说明里的数字是数值的又一份副本。

**从内容数据自动生成整段说明。** 完全不用手写。没有选，因为带触发和条件的效果很难生成通顺的中文，生成器本身的工作量也大。

## Acceptance criteria

- 角色技能、天赋、敌人和首领的数值只出现在 `src/content/` 里，combat.md 开头写明具体数值以内容数据为准。
- 技能、天赋、羁绊技和秘传技的说明里，会随数值调整而变的数字都用占位符，阿莎姬现有天赋节点的说明也改成这种写法。
- 写错的占位符会让 `npm test` 失败。

## Risks

- combat.md 里的数字会随调整变旧，读者可能把它们当成现行数值。能提醒读者的只有开头那句说明。
- 审稿要读 TS 文件，没有一张能横向比较平衡的总表。
- agent 起草的技能、天赋和敌人可能偏离角色档案，要靠审稿发现。
